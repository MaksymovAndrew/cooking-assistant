# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository. Humans will find it a useful map too.

## Repository layout

Two-app monorepo (no workspaces - each side has its own `package.json`):

- [backend/](backend/) - Node.js + Express 5 + TypeScript + PostgreSQL (`pg`) API on port `3000`; helmet, express-rate-limit, pino, and zod provide operational hardening and input validation; source lives under [backend/src/](backend/src/)
- [frontend/](frontend/) - React 19 + TypeScript + Next.js 16 (App Router) on port `8080` (SCSS modules)
- Database schema is managed by `node-pg-migrate`: SQL migrations live in [backend/migrations/](backend/migrations/) (the initial one captures the full current schema) and reference/sample data is loaded by [backend/src/scripts/seed.ts](backend/src/scripts/seed.ts).
- Root [package.json](package.json) is an orchestration shim: it pulls in `concurrently` and exposes scripts that drive both sub-packages. It also holds the single shared project version (see [Versioning](#versioning) below).
- [CHANGELOG.md](CHANGELOG.md) at the root is the single changelog for the whole project.
- Licensed **GNU AGPLv3** ([LICENSE](LICENSE)). Copyleft with the network clause: a modified version run as a network service must publish its source to that service's users. Keep the three `package.json` `license` fields (`AGPL-3.0-or-later`) and the README section in step with the LICENSE file if it ever changes.

## File size and where code lives

Read this before writing code: it answers "where does this go", so nothing has to be rediscovered by searching. When you brief another agent, point it here instead of restating it.

**Size.** The working norm is **100 lines per file and per function** (blank lines and comments not counted, tests exempt). ESLint's `max-lines`/`max-lines-per-function` sit at **250** on both sides - a hard ceiling that catches accidents, not a budget to spend. A file heading past 100 is holding something that belongs elsewhere: split it by cohesion (a sub-component, a hook, a util, a types module), never by cutting at an arbitrary line, and never with `eslint-disable` or an exception list.

**A component is markup.** It takes data, renders JSX and wires handlers - no business logic lives in it:

- pure logic (computing, formatting, mapping, validation rules, classifying an error) → a function in `utils/`, with its own test in `utils/__tests__/`
- state and effects → a hook in `hooks/`; the hook keeps the state, the rules it applies stay in `utils/` (`useRecipeFormValidation` → `utils/recipeFormValidation.ts`)
- a data shape used by more than one file → `types/`; a component's own props interface stays beside the component
- a large or repeated block of JSX → a sub-component in the same folder (`RecipeHero/RecipeHeroActions.tsx`)
- user-facing text → an i18n key; a magic number → a named constant; server data → an RTK Query endpoint

Anything written three times is extracted (rule of three), and a condition with 3+ parts becomes a named constant (a lint rule). A new util or hook ships with its test.

## Common commands

Preferred - from repository root ([package.json](package.json)):

```bash
npm install              # installs root + auto-runs postinstall in backend & frontend
npm start                # OR npm run dev - concurrently boots backend (3000) + frontend (8080)
npm run start:backend    # backend only (tsx watch)
npm run start:frontend   # frontend only (next dev)
```

Every per-app quality command has a root aggregate too - `lint`, `lint:fix`, `lint:sonarjs`, `stylelint`, `stylelint:fix`, `typecheck`, `test`, `test:coverage`, `build` (frontend), `build:backend`, `verify` - and all scripts are cross-platform (plain node CLIs, no shell-specific syntax), so they behave identically on Windows, macOS and Linux. Two more root scripts cover the slower suites, deliberately kept out of `test`/`verify`/the pre-commit hook: `test:e2e` (Playwright smoke suite against a live dev stack, see [e2e/](e2e/)) and `test:db` (Testcontainers real-Postgres repository suite, see [backend/src/test/db-integration/](backend/src/test/db-integration/)) - both need Docker.

The root `postinstall` hook (`npm --prefix backend install && npm --prefix frontend install`) means a single `npm i` at the root populates all three `node_modules`. Don't add a separate `install:all` script.

Per-app, if you need it directly:

Backend ([backend/](backend/)):

```bash
npm run dev        # tsx watch -> http://localhost:3000
npm start          # tsx src/index.ts, no auto-reload
npm run typecheck  # tsc --noEmit
npm run lint       # eslint .
npm run test       # jest via ts-jest
npm run migrate    # node-pg-migrate: apply all pending migrations (up); `migrate down` rolls back one
npm run seed       # load reference + sample data (idempotent)
```

Frontend ([frontend/](frontend/)):

```bash
npm run dev      # next dev -> http://localhost:8080
npm run build    # next build (type-checks as part of the build)
npm run preview  # next start - serves the production build
npm run lint     # eslint .
```

Both sides have a Jest suite with an 80% coverage gate (`test` / `test:coverage`). Backend uses ts-jest + Supertest; frontend uses @swc/jest + React Testing Library + jsdom (~220 co-located `__tests__` files).

Backend test conventions (match these when adding tests):

- Business-logic unit tests stay no DB, no Express. Use cases and domain entities are tested with fake repositories/ports built from `jest.fn()`; mock only what is necessary.
- Middleware unit tests call the middleware directly with mocked `req`/`res`/`next`.
- Supertest integration tests use `buildTestApp` with fake repositories/ports. They exercise real routes, auth middleware, controllers, use cases, and `errorHandler` without a database.
- Pg-repository tests run against a real Postgres via Testcontainers, in a separate suite: [backend/src/test/db-integration/](backend/src/test/db-integration/), run with `npm run test:db` (its own `jest.db.config.js`, a `globalSetup`/`globalTeardown` pair that starts one shared container and applies migrations, and a `testPool.ts` helper each test file's worker process reads the connection info from). Not part of `npm test`/the pre-commit hook (needs Docker, slower) - it has its own CI job instead. Do not add mock-pool SQL-string tests as a substitute for this suite.
- Unit tests are co-located in `__tests__/` next to the unit, named `<Unit>.test.ts`; HTTP integration tests live in `backend/src/test/integration/`.
- Test names start with "should": `it("should ...")`.
- Assert domain errors by code with the custom matcher `expect(err).toBeAppError(Class, ERROR_CODES.X, status, detail?)` ([backend/src/test/jest.setup.ts](backend/src/test/jest.setup.ts)), and compare HTTP error bodies with `errorBody(ERROR_CODES.X)` ([backend/src/test/helpers/errorBody.ts](backend/src/test/helpers/errorBody.ts)); capture thrown errors with `catchError` / `catchSyncError` ([backend/src/test/helpers/assertions.ts](backend/src/test/helpers/assertions.ts)).

Frontend test conventions (read [frontend/src/test/jest.setup.ts](frontend/src/test/jest.setup.ts) and [frontend/jest.config.cjs](frontend/jest.config.cjs) first):

- Co-located `__tests__/` named `<Unit>.test.ts(x)`; `it("should ...")`; prefer `act` over `waitFor`.
- Both RTK Query service tests and component/page/hook tests `jest.mock("api/client")` and drive real RTK Query hooks through a real store (`makeTestStore`/`setupStore`), asserting against the typed mocks in [frontend/src/test/apiClientMock.ts](frontend/src/test/apiClientMock.ts) (`mockedGet`/`mockedPost`/...). There is no separate per-domain wrapper to mock instead - server data flows through `redux/services/*`, not through `api/*`.
- Render with `renderWithRouter` from [frontend/src/test/router.tsx](frontend/src/test/router.tsx) (defaults to a non-root route; asserts navigation via the shared `mockNavigate`). `config/env` and `config/logger` are mocked globally via `moduleNameMapper`, and so are `next/navigation` and `next/link` - [frontend/src/test/nextNavigationMock.ts](frontend/src/test/nextNavigationMock.ts) holds a real, writable URL, so hooks built on search params are exercised rather than stubbed (`setTestLocation` / `setTestParams` seed it). No test mocks the router itself.
- No `as any`; real domain types from `types/*` for fixtures.

End-to-end smoke tests live at the repo root in [e2e/](e2e/) (Playwright, [playwright.config.ts](playwright.config.ts)), run with `npm run test:e2e`. They boot both dev servers (reusing an already-running `npm start` locally; fresh servers in CI) and drive real login/CRUD flows through a Chromium browser - `smoke.spec.ts` is the golden path (one of only two specs that register their own account, since registration/login is the feature it exercises), `core-flows.spec.ts` covers edit/delete/pantry/theme-toggle flows expected to survive the upcoming page redesign, `routes-smoke.spec.ts` visits every route in [frontend/src/constants/routes.ts](frontend/src/constants/routes.ts) (list/detail/form pages plus the not-found page) so a redesign that blanks a page fails here even without a dedicated flow test, `shopping-list.spec.ts` adds, reorders, ticks off and clears shopping list items, `menu-missing-ingredients.spec.ts` checks a menu's missing ingredients against a real pantry and sends them to the shopping list, `diet-preferences.spec.ts` avoids an allergen and an ingredient in the profile and checks the recipe card mark and the hide filter, `tags.spec.ts` creates a private tag on a recipe, filters the list by it and deletes it, `search-filter.spec.ts` exercises recipe/menu search, type/category filters and sort order, `ownership.spec.ts` verifies the public-read/owner-only-write contract (view as another user, hidden edit/delete controls, 404 on a non-owner's update), `pantry-details.spec.ts` covers purchase-history viewing and full ingredient removal, `photos.spec.ts` adds, shows and removes a recipe photo and a profile photo through the real upload pipeline, `ratings.spec.ts` rates another user's recipe, lists it under the top-rated filter, changes and takes back the vote, and checks the owner and a guest get no stars, and `session-revocation.spec.ts` signs one account in on two browsers, changes the password in one and checks the other is signed out while the first stays in (it registers its own account, since changing a shared account's password would end every other spec's session). `global-setup.ts` registers two shared accounts (`primary`/`viewer`) once per run and saves their sessions via Playwright `storageState`; every spec besides `smoke.spec.ts` reuses one of these instead of registering its own, keeping the whole suite's login/register traffic well under the auth rate limiter - see [e2e/sharedAccounts.ts](e2e/sharedAccounts.ts). Not part of `npm test`/the pre-commit hook - it has its own CI job instead. The suite is one client driving the whole API, and every server-rendered page adds its own calls on top, so both the CI job and a local run need `RATE_LIMIT_MAX` well above the 300/min default - otherwise the specs that run last fail with a 429.

## Versioning

The whole project shares ONE version, stored in the root [package.json](package.json). It increments by one each release (for example `1.3 -> 1.4`).

A release also bumps `backend/package.json` and/or `frontend/package.json` up to the shared number, but only for the side(s) actually changed. An untouched side keeps its old number. So a package version is a marker of "the last release in which this package changed" and may skip numbers - it is NOT strict SemVer.

Worked example:

- `1.2` changed only the backend: `backend` went to `1.2`, `frontend` stayed on its previous number.
- `1.3` changed both: both went to `1.3`.
- A later `1.5` that changes only the backend takes `backend` straight to `1.5` (skipping `1.4`, which it was not part of); `frontend` stays where it was.

Rule of thumb: the version takes care of itself. The pre-commit hook runs [scripts/release-version.mjs](scripts/release-version.mjs) in `precommit` mode: on a `release/X.Y` branch it reads the target from the branch name, sets the root `package.json`, raises only the side(s) with changes vs `main`, syncs the lockfile `version` fields, and `git add`s whatever it rewrote so the bump rides along in that same commit (silent no-op when everything already matches; runs even under `SKIP_CHECKS=1`, unlike the other checks; a manual mid-release patch like `3.3.1` in the root wins over the branch default). A `hotfix/X.Y.Z` branch (see "Hotfix flow" below) is the same mechanism with the exact patch version already in the branch name, so there's nothing to guess. `npm run bump` (optionally `-- 3.4` or `-- 3.9.1`) runs the same logic manually. Do not use `npm version` or edit version fields by hand.

## Changelog

There is ONE changelog: root [CHANGELOG.md](CHANGELOG.md). There are no per-package changelogs.

1. Each release is a `## x.y - YYYY-MM-DD` heading containing `### Backend` and/or `### Frontend` subsections. Omit the subsection for a side that was not touched.
2. While work is in flight, add entries under the top `## Unreleased` heading; at release time, move them into a new dated version heading and leave `## Unreleased` empty.
3. Write entries from the user's perspective, not the code's. Good: "Filter recipes by cooking time range". Bad: "Add `time_min`/`time_max` query params to `/api/recipes-by-filters`".
4. Use Keep a Changelog wording where it helps (`Added`, `Changed`, `Fixed`, `Removed`, `Security`), but the `### Backend` / `### Frontend` split is the primary structure here.
5. **Every release with user-visible changes also gets an entry in [frontend/src/i18n/locales/en/news.json](frontend/src/i18n/locales/en/news.json)** and in the same file of every other language - the in-app "What's new" popup, read by [frontend/src/utils/newsItems.ts](frontend/src/utils/newsItems.ts). Add ONE new key to the TOP of `items` (object key order = display order, newest first - `getLatestReleaseDate()` reads the first entry for the "N new" badge, so a key added anywhere else silently breaks it) dated with the release date, with a short title and a one/two-sentence description in the same friendly, non-technical tone as the existing entries. Curate, don't transcribe: one news entry can summarize several related CHANGELOG bullets (e.g. password reset + email verification + change password all became one "Password reset & email verification" entry in 3.4); skip internal/technical fixes with no user-facing effect. A release with no user-visible changes (ops/infra only) gets no news entry.

## Commit and PR conventions

One commit = code change + version bump + changelog update. Bundle them together.

A release is normally SEVERAL such commits, not one - split the work into logical portions (a feature, a fix, a refactor) and commit each on its own, all on the same `release/X.Y` branch under one PR. The PR is squash-merged, so the commit count costs nothing downstream. The version hook only rewrites files on the first commit of the branch; every later commit is a silent no-op, so nothing special is needed for portion two onward. The PR description always covers the whole release, not the latest commit.

Message format: `<version>: <short description>` - the shared target version, for example:

```
1.4: add cooking-time filter to the recipe list
1.5: fix menu deletion leaving orphaned rows
```

Optionally note the side when only one changed: `1.4 (frontend): ...`. The version in the message lets GitLens blame hover show which release a line landed in (a confirmed user preference).

Hard rules:

- Do NOT create git tags for versions. Exception: a `v*` deploy tag (e.g. `v2.0`) triggers the production
  deploy pipeline - only the user creates these, never an agent.
- Do NOT add a `Co-Authored-By` trailer to commits.
- Do NOT commit directly to `main`. Branch from `main`, named after the release (for example `release/1.4`), commit there, push, and open a PR for review.
- Never `git push` without explicit user permission.

Preferred git commands (use these exact forms):

```
git switch main          # switch to existing branch
git switch -c release/X.Y   # create and switch to new branch
git add .                # stage all changes
git push origin release/X.Y  # push branch (no -u flag)
```

### PR / MR description

Keep the body short and to the point - what was **added** and what was **fixed**, nothing else. Two optional bulleted sections; omit either if it has nothing:

```
<version>: <same text as the commit title>

Added:
- <new capability, in user-facing language>

Fixed:
- <bug fixed, in user-facing language>
```

PR title = the commit title (`<version>: <description>`). One bullet per change, in plain language (what it means for a user, not the code). Default to just `Added`/`Fixed`; only reach for `Changed`/`Removed`/`Security` if a change is genuinely neither. No verification/"Checks" line, no AI-tool or Co-Authored-By attribution.

### Quality gates (CI + hooks)

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on every PR and on push to `main`: a root `format` (Prettier check), then per side `lint` (ESLint), `typecheck`, `sonarjs` (SonarJS lint), and `test:coverage` (Jest, 80% gate); the frontend additionally runs `build` (`next build`, with `NEXT_PUBLIC_SITE_URL` set to a placeholder) and `stylelint`. Two more jobs run the slower suites: `e2e` (Playwright smoke suite, starts both dev servers + a Postgres service + runs migrate/seed) and `test-backend-db` (Testcontainers real-Postgres repository suite - no `services:` needed, it manages its own container via the runner's Docker daemon). A `ci-success` job aggregates all of them and is the single required check - all must be green to merge. The same quick suite runs locally before a commit via the Husky `pre-commit` hook (lint-staged + both sides' typecheck/lint/sonarjs/tests, plus frontend stylelint); `pre-push` both blocks pushing straight to `main` and runs the frontend build. `npm run verify` reproduces the CI gates locally in one command (e2e/db-integration are deliberately excluded - run `test:e2e`/`test:db` separately when Docker is available). Hosted SonarCloud is not wired up (no `SONAR_TOKEN`); the local `sonarjs` lint covers the static-analysis role for now.

**Escape hatches (ops-only commits - never use when touching `backend/src` or `frontend/src`):**

- `git skip-checks commit -m "<msg>"` / `git skip-checks push origin <branch>` - the convenient form. `git skip-checks <cmd>` is a repo-local alias (in `.git/config`, NOT global; auto-installed on `npm install` via `scripts/setup-skip-alias.mjs`) that runs the command with `SKIP_CHECKS=1`. Scoped to that one command and works in any shell - a plain `git commit` afterwards runs the full checks as usual. Use only for pure ops-only changes: `.github/workflows/`, `.husky/`, docs, changelog.
- Under the hood, `SKIP_CHECKS=1` on a commit skips all local pre-commit checks AND, via the `prepare-commit-msg` hook, auto-stamps `[skip-checks]` onto the commit subject so all 11 CI jobs skip too; `ci-success` still passes (`skipped != failed`), so the PR can merge. On a push it also skips the pre-push frontend build (`SKIP_HOOKS=1` stays as a backward-compat alias). The direct-push-to-main block in `.husky/pre-push` is a policy guard and is NOT bypassed by either flag.
- In CI a `gate` job reads the head commit message (it checks out the PR head sha, since `pull_request` events carry no `head_commit`) and the other jobs skip when it finds `[skip-checks]`. So the commit marker is authoritative on both `push` and PR - the PR title does not need it. The PR title is still honored as a fallback. CI re-evaluates per push, so the tip commit of the latest push decides.

**Hotfix flow (`hotfix/X.Y.Z` branch):** for an urgent patch where the fix is small and well-understood, branch as `hotfix/3.9.1` (exact three-part version, matched by regex in both the hooks and [scripts/release-version.mjs](scripts/release-version.mjs)) instead of `release/X.Y`. This is fully automatic - no `SKIP_CHECKS`/`git skip-checks` needed:

- `pre-commit` still auto-bumps the version (the branch name already is the exact target, nothing to guess), but runs **only typecheck** (backend, frontend, `typecheck:e2e`) instead of the full lint/test/stylelint suite - a real check still blocks a broken commit, just a fast, narrow one.
- `prepare-commit-msg` auto-stamps `[skip-checks]` on the commit, so CI's heavy jobs skip the same way they would under the manual escape hatch.
- `pre-push` auto-skips the frontend build.
- Everything else is unchanged: still a PR into `main` (the `pre-push` direct-to-main block is not bypassed), still no tags from an agent.

This is a narrower, unconditional trigger than the ops-only escape hatch above - it fires on branch name alone, with no file-path check. That's a deliberate trade: typecheck is the one guardrail kept in every case, on the reasoning that a genuine hotfix is small enough for that to be a meaningful signal. Don't use a `hotfix/*` branch to sneak untested application logic past review - if the change is more than a narrowly-scoped, already-understood fix, use a normal `release/X.Y` branch and get the full gate.

## Required configuration

1. PostgreSQL connection in [backend/src/config/env.ts](backend/src/config/env.ts) reads the `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` environment variables, falling back to conventional local-Postgres defaults when unset (the literals live in `env.ts`). Those defaults are dev-only: `assertSecureProductionDb` refuses to start in production if the password is still the default. Env values are parsed with zod on startup, so invalid ports or logger levels fail fast with a clear configuration error. `JWT_SECRET_KEY` is optional in development and required in production (`assertProductionSecrets`, run at config load beside the database and email guards) - without that guard a deploy missing it starts, passes both health checks, and 500s on every sign-in; JWT code still reads it lazily, and it must be at least 32 characters when set. [backend/src/db.ts](backend/src/db.ts) consumes that typed config.
2. Backend `.env` is gitignored. Copy [backend/.env.example](backend/.env.example) to `backend/.env` and fill it in - `config/env.ts` reads it with Node's own `process.loadEnvFile` (no `dotenv`; a variable already set in the environment wins, and a missing file is fine, which is how production runs). It holds `JWT_SECRET_KEY` (read lazily through [backend/src/config/env.ts](backend/src/config/env.ts) by JWT auth code) plus the `DB_*` keys, `NODE_ENV`, `PORT`, optional `LOG_LEVEL` for pino, `CORS_ORIGIN` (the allowed frontend origin), `COOKIE_DOMAIN` (empty in dev for a host-only auth cookie; the shared parent domain in production so subdomains share the session - `Secure` flips on automatically when `NODE_ENV=production`), and `RESEND_API_KEY`/`EMAIL_FROM` (both optional, must be set together - transactional email for password-reset/email-verification links; leave both empty to use the logging fallback adapter, which logs the link instead of sending it, so nothing 500s locally without a real Resend account). Without `JWT_SECRET_KEY`, login and every protected route return a 500 configuration error. Tests set a long `JWT_SECRET_KEY` in [backend/src/test/jest.setup.ts](backend/src/test/jest.setup.ts). When you add a new env key, add it (without a value) to `.env.example` too.
3. CORS in [backend/src/app.ts](backend/src/app.ts) allows the origin from the `CORS_ORIGIN` env var (default `http://localhost:8080`, via `config.corsOrigin`) and runs with `credentials: true`; the app mounts `cookie-parser` so the browser can send the httpOnly auth cookie cross-origin. For a different frontend port or a deployed origin, set `CORS_ORIGIN` in `.env` - no code change.
4. Database setup uses `node-pg-migrate` (configured to reuse the same `config.db` as the app, so there is no separate `DATABASE_URL`). Migrations are the only source of truth for the schema. On a fresh DB run `npm run migrate` (or `migrate up`) then `npm run seed` from the root or `backend/`; `seed` is idempotent, so it is safe to re-run. New migrations are scaffolded with `npm --prefix backend run migrate:create <name>` (SQL files with `-- Up Migration` / `-- Down Migration` markers).

**Trigger:** push a `v*` tag (e.g. `v2.0`) - user does this, never an agent. GitHub Actions
([.github/workflows/deploy.yml](.github/workflows/deploy.yml)) then:

1. Builds `cooking-backend` Docker image via `tsup` + `node`, pushes to GHCR. The runtime stage drops to the unprivileged `node` user (`USER node`) - keep it that way. The one directory it writes is `/app/uploads` (uploaded photos, the `uploads` named volume), which the image creates and hands to `node` itself: a volume mounted at a path the image lacks is created root-owned, and the first upload would fail.
2. Builds `cooking-frontend` Docker image from Next's `standalone` output, pushes to GHCR. The runtime is a Node process that renders pages on request, listening on **8080** as the unprivileged `node` user (a low port would need root). `.next/static` and `public/` are copied separately - the standalone trace contains neither, and forgetting them ships a site with no stylesheets. `GET /health` is the container's liveness probe.
3. Connects to the server over SSH and runs `/srv/bin/deploy.sh` ([deploy/deploy.sh](deploy/deploy.sh)): pull images, run migrations + seed as a one-shot compose container, start the stack, wait for **both** containers to report healthy - and restore the previous `IMAGE_TAG` if either never does. Gating on the backend alone was enough while the frontend was static files; a render process can start and still serve nothing. After a healthy deploy it cleans up after itself: this project's images other than the current and the previous tag (the rollback target) are removed - never other projects' images, so no blanket `prune -a` - along with hand-made `*.bak-*` copies older than 14 days in `/srv/bin` and the stack directory.

Both build jobs run on `ubuntu-24.04-arm` and target `linux/arm64`. This is not optional: the server is ARM, an x86 image does not start on it at all, and emulating arm64 on an x86 runner is roughly twenty times slower. ARM runners are free for public repositories.

`workflow_dispatch` takes a tag input, so any published tag can be re-deployed or rolled back from the Actions tab without inventing a new one.

**Infrastructure:** one self-hosted ARM server (Ubuntu 24.04, 2 OCPU / 12 GB, Frankfurt), everything in Docker. The deployed shape lives in [deploy/](deploy/) and is copied onto the server - the repo is the source of truth for it, not the machine.

- Shared entrypoint `/srv/edge`: Caddy on 80/443 with automatic Let's Encrypt certificates, importing one file per project from `sites/`. Adding a project never edits a shared file. **No file under [deploy/](deploy/) is applied by any pipeline** - the deploy key is pinned server-side to a forced command, so the workflow can ask for a deploy and nothing else; it cannot copy a byte. Every file there is put on the server by hand, and a release that changes one carries that copy as a required manual step: `deploy.sh` to `/srv/bin/`, `docker-compose.yml` to `/srv/cooking-assistant/`, and the Caddyfile into `/srv/edge/sites/cooking-assistant.caddy` followed by a reload. Caddy runs as a container, so the reload is `docker exec caddy caddy reload --config /etc/caddy/Caddyfile` - there is no `caddy` binary on the host, and `sudo caddy reload` only answers `command not found`. Two of those bite quietly. `deploy.sh` gates on the frontend reporting healthy, so copying it without the compose file that defines that health check makes every deploy roll back. And a proxy left on the wrong port reports a fully green deploy while every visitor gets a 502 - both container health checks run inside the project network, so nothing catches it.
- Project stack `/srv/cooking-assistant`: `backend`, `frontend`, `postgres`, plus a `migrate` service behind the `tools` profile so `up` never starts it.
- **Uploaded photos live in the `uploads` named volume** on the backend (`MEDIA_DIR`, default `uploads` relative to the working directory, i.e. `/app/uploads` in the image). It outlives every container, and it is user content: `/srv/bin/backup.sh` has to archive it alongside the database dump, or a lost disk loses every photo.
- **No application container publishes a host port.** Caddy reaches them over the external `edge` network by alias (`cooking-backend`, `cooking-frontend`); Postgres is reachable only from the project's own network. This is the actual protection for the database - Docker inserts its rules into `nat` ahead of the `INPUT` chain, so a published port is reachable regardless of the host firewall.
- Images: `ghcr.io/<repo-owner>/cooking-{backend,frontend}` (owner resolved from `github.repository_owner` in the workflow, not hardcoded - it must track whoever currently owns the GitHub repo). The packages are public, so the server pulls them without registry credentials.
- DB: PostgreSQL 18 in a container. The volume is mounted at `/var/lib/postgresql`, not the pre-18 `/var/lib/postgresql/data` - PG18 moved its data directory to `/var/lib/postgresql/18/docker`, and the old path keeps working right up until the container is recreated, then the data is gone.
- Ops scripts on the server: `/srv/bin/backup.sh` (nightly 03:30 - dump, restore it into a throwaway database to prove it works, prune) and `/srv/bin/status.sh` (one-shot health report: resources, platform, per-project).

**Config at runtime** (`/srv/cooking-assistant/.env` on the server, mode 600, never in repo): `JWT_SECRET_KEY`, `DB_*`,
`NODE_ENV`, `CORS_ORIGIN`, `COOKIE_DOMAIN`, `LOG_LEVEL`, `MEDIA_DIR`, `RESEND_API_KEY`, `EMAIL_FROM`
(transactional email for password-reset/email-verification links - both must be set together; the
production backend has no logging-fallback safety net once real users depend on these
flows, so treat them as required for prod even though they're optional in dev). Four of them are easy to get wrong:

- `DB_SSL=false` is **required**. Production defaults SSL on, and the co-located Postgres container serves no TLS, so the backend never starts without it.
- `TRUST_PROXY_HOPS=1` - exactly one proxy (Caddy) sits in front. Server-side rendering does not add a hop: Express reads the last `X-Forwarded-For` entry, which the nearest trusted proxy appends, so a rendered request is still attributed to the real visitor - **provided the frontend forwards that header** on every server-side call into the API. Dropping it would collapse all rendered traffic onto one client for the rate limiter.
- `CORS_ORIGIN` must match the site origin exactly. A wrong value is invisible to `curl`, which ignores the header, while every browser request is blocked - verify it in a browser or by reading `Access-Control-Allow-Origin` explicitly.
- `IMAGE_TAG` is rewritten by `deploy.sh` on every deploy, and pointing it back at the previous value is what a rollback is.

**Deploy auth** (GitHub → server, no password): an SSH key pinned server-side in `authorized_keys` to
`command="/srv/bin/deploy.sh"` with no pty and no forwarding, so a leaked key can trigger a deploy and nothing else.
The workflow's only argument reaches the script as `SSH_ORIGINAL_COMMAND` in the form `<owner> <tag>`, and both are
validated there before use. The owner travels with every deploy rather than living in the server's `.env` because the
GHCR namespace follows `github.repository_owner`: a repository transfer changes it, and a stale server-side copy breaks
the deploy silently - which is exactly how 3.9.1 and nearly 4.3 were lost.
GitHub repo secrets: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `SSH_KNOWN_HOSTS`.
GitHub repo variables: `API_DOMAIN` and `APP_DOMAIN` - baked into the frontend image as `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_SITE_URL` at build time, so changing either address needs a rebuilt image, not a restart. The second is what canonical and social URLs resolve against; a build without it fails rather than shipping links to localhost.

**Uptime monitoring (not wired up yet - manual step, no code involved):** point any free uptime
checker (e.g. UptimeRobot, Better Uptime, Freshping) at `GET /api/health` on the API domain,
on a 1-5 minute interval, alerting on a non-200 response. It is a public, unauthenticated
liveness endpoint - no new backend code needed, just external configuration. This matters more than it
used to: a managed platform used to probe the app and restart it, and now nothing does.

**Cookie in prod**: `httpOnly`, `secure` (auto when `NODE_ENV=production`), `sameSite: Lax`,
`domain: .<app-domain>` (leading dot so the app and api subdomains share the session).

**When adding env vars**: add to `backend/.env.example` AND [deploy/.env.example](deploy/.env.example), set the
value in the server's `.env`, never commit values. Editing `.env` takes effect only after the container is
recreated - the backend reads its environment once at startup.

## Database workflow

Three kinds of database change, and they are NOT the same thing - pick by what you are changing:

1. **Runtime data** (a user creates a recipe, adds a pantry ingredient, etc.) - just flows in through the normal API/repository `INSERT`s while the app runs. No migration, no seed, nothing to edit. This is the vast majority of writes.
2. **Seed / starter reference data** (the unit_measurement / recipe_types / menu_category rows and the sample ingredients that every fresh DB should start with) - lives in [backend/src/scripts/seed.ts](backend/src/scripts/seed.ts).
3. **Schema change** (a new table, column, constraint, or index - the _shape_ of the DB) - a new migration in [backend/migrations/](backend/migrations/).

**To add or change an ingredient:** the catalog is data, not code - 739 entries in [backend/src/scripts/catalog/catalogData.json](backend/src/scripts/catalog/catalogData.json), keyed by `slug`. Add an object (`slug`, `category`, `nameEn`/`nameRu`/`nameUk`/`namePl`, `unit`, `allergens`, `daysToExpire`, `seasonality`, `storageCondition`, `caloriesPerUnit`), then run `npm --prefix backend run catalog:locales` to regenerate the frontend `catalog.json` locale files (ingredient names, categories and allergens), then `npm run seed`. Names follow the catalog rules in [frontend/README.md](frontend/README.md#translations) - what a shop label says, capitalised, no stress marks - and `scripts/catalog/__tests__/catalogNames.test.ts` rejects the mechanical slips. A name you correct also goes into `translationOverrides.json`, which the dev-only rebuild (`buildCatalogData.ts`) applies over its dumps, so a rebuild cannot bring the old one back. Seeding upserts (`ON CONFLICT (slug) DO UPDATE`), so it re-runs on every deploy and keeps the DB in sync with the JSON - editing an existing entry propagates, it isn't insert-once. Commit the JSON, the regenerated locales, and nothing else. Do NOT write a migration for this - ingredients are rows, not schema.

**To make a schema change (the only time you write a migration):**

1. `npm --prefix backend run migrate:create <short-name>` - scaffolds `migrations/<timestamp>_<short-name>.sql` with empty `-- Up Migration` / `-- Down Migration` sections.
2. Fill in `Up` (the change, e.g. `ALTER TABLE ingredients ADD COLUMN calories INTEGER;`) and `Down` (the exact reverse, e.g. `ALTER TABLE ingredients DROP COLUMN calories;`).
3. `npm run migrate` - applies only the new file (already-run migrations are recorded in the `pgmigrations` table and skipped). `npm run migrate down` rolls back the last one via its `Down` section.
4. Update the code that uses the new shape (the relevant `Pg*Repository` SQL/types, and a zod schema if it is request input), then commit the migration file together with that code.

The timestamp prefix on a migration filename only sets apply order (later timestamp = runs later); never rename or reorder existing migration files once they have been applied anywhere.

**How it is wired (read before adding any DB feature):**

- Migrations are plain SQL files in [backend/migrations/](backend/migrations/), one file per change, using node-pg-migrate's `-- Up Migration` / `-- Down Migration` markers (the `migrate:create` script scaffolds them; `migration-file-language` is `sql`). node-pg-migrate records applied migrations in a `pgmigrations` table and skips them next run. No `pgm.*` JS DSL - keep migrations as raw SQL.
- The runner and seed are tsx scripts in [backend/src/scripts/](backend/src/scripts/) (`migrate.ts`, `seed.ts`), placed under `src/` so they are typechecked and linted (they are excluded from coverage by the `collectCoverageFrom` allowlist). `migrate.ts` calls node-pg-migrate's programmatic `runner({ databaseUrl: config.db, ... })` and parses `up`/`down`/`--fake` from `argv`; `seed.ts` opens its own short-lived `new Pool(config.db)`. Both reuse `config.db` from [backend/src/config/env.ts](backend/src/config/env.ts) - the same `DB_*` source as `db.ts`; there is deliberately NO separate `DATABASE_URL`. Both log through the pino `logger` (the global `no-console` rule applies) and set `process.exitCode = 1` on failure.
- The backend compiles with `module`/`moduleResolution: "NodeNext"` (files stay CommonJS because there is no `"type": "module"`), so packages that declare types through an `exports` map (like node-pg-migrate) resolve natively. Do not add type shims for `exports`-map packages.
- Seeding must stay idempotent so re-running it never duplicates or errors: ingredients upsert on `slug` (`ON CONFLICT (slug) DO UPDATE`, batched 100 rows at a time in [seedIngredientsFromCatalog.ts](backend/src/scripts/seedIngredientsFromCatalog.ts)); reference tables without a unique constraint (`unit_measurement`, `recipe_types`, `menu_category`) use `INSERT ... SELECT ... WHERE NOT EXISTS`. Look the unit id up by `unit_name` (a subquery/JOIN) - never id-based `UPDATE`s.
- The initial migration is the full current schema, not a replay of historical ALTERs. Keep the misspelled column name `quantity_person_ingradient` - it is the real column.
- Setup is `npm run migrate` + `npm run seed` on a fresh DB. All scripts work from the repo root or `backend/`.

## Architecture

### Backend - clean (layered) architecture

Express app creation in [backend/src/app.ts](backend/src/app.ts) mounts operational middleware first (`helmet`, `pino-http`, CORS, and the 100kb JSON body parser), then the public health check and the domain routers under `/api`; [backend/src/index.ts](backend/src/index.ts) only wires the real composition root into `createApp`, listens, and drains the HTTP server plus pg pool on `SIGTERM`/`SIGINT`:

- `health.routes` -> public `/health` liveness probe
- `user.routes` -> register, login, logout, current-user profile and language, password reset, email verification
- `ingredient.routes` -> ingredient catalog list
- `recipe.routes` -> recipe CRUD, filters, stats
- `type.routes` -> recipe types (read-only list; CRUD removed in 1.40)
- `userIngredients.routes` -> per-user pantry + purchase history
- `menu.routes` -> menu CRUD + per-user filter
- `menuCategory.routes` -> menu category list, menus by category
- `calorie.routes` -> calorie intake log and calorie goal
- `favourite.routes` -> add/remove a recipe or menu favourite (`PUT`/`DELETE /recipe/:id/favourite`, `/menu/:id/favourite`)
- `rating.routes` -> rate a recipe or menu 1-5 or take the vote back (`PUT`/`DELETE /recipe/:id/rating`, `/menu/:id/rating`); nobody rates their own
- `shoppingList.routes` -> per-user shopping list: items CRUD, clear checked, reorder, add catalog ingredients with merge
- `photo.routes` -> a record's or the account's photo: `PUT`/`DELETE /recipe/:id/photo`, `/menu/:id/photo`, `/me/avatar` (owner only; the body is the image itself)
- `media.routes` -> public `GET /media/:file` serving stored photos, mounted **before** the global limiter (a page of cards is dozens of requests) and left out of request logs
- `dietPreferences.routes` -> the viewer's avoid list: `GET /diet-preferences`, one-at-a-time `PUT`/`DELETE` for an allergen (`/diet-preferences/allergens/:slug`) and a catalog ingredient (`/ingredient/:id/avoid`)
- `tag.routes` -> the viewer's private recipe tags: `GET`/`POST /tags`, `PATCH`/`DELETE /tags/:id`, and `PUT /recipe/:id/tags` to replace the set on one recipe

The backend is organised in layers with dependencies pointing inward (Dependency Rule). Wiring is built once in [backend/src/composition-root.ts](backend/src/composition-root.ts): `buildControllers(deps)` is reusable for tests, and the default export uses the real Pg repositories/services.

- **Routes** ([backend/src/routes/](backend/src/routes/)) are factory functions `(controller) => router` for domain routes, plus controller-free infrastructure routes such as health. They map `METHOD /path` directly to a controller handler and (almost always) guard it with `authenticateToken`. **A path is never written as a literal in a router** - every one lives in [backend/src/constants/routes.ts](backend/src/constants/routes.ts) (`ROUTES`, grouped by domain, router-relative; `API_PREFIX` is the `/api` mount and `HEALTH_PATH` the one full path, derived from both because request logging filters the probe out). Adding an endpoint means one entry there and one `router.<method>(ROUTES...)` line. The public routes are `/health`, `/register`, `/login`, `/logout`, `/forgot-password`, `/reset-password`, and `/confirm-email`; each of those (plus `/change-password`, `/resend-verification-email`, and `/me`'s `DELETE`) has its own dedicated limiter in [backend/src/middleware/rateLimit.ts](backend/src/middleware/rateLimit.ts), plus a global limiter (`createGlobalLimiter`) mounted ahead of every domain router in `app.ts`. Express 5 forwards rejected promises from async handlers to the error middleware.
- **Controllers** ([backend/src/controller/](backend/src/controller/)) are thin HTTP adapters: classes whose handlers are arrow-function properties (so `this` is bound). A handler reads input from `req` (params/body/query/`req.user.id`), calls a use case, sends the response. No try/catch - errors propagate to the error middleware.
- **Validation** ([backend/src/application/validation/](backend/src/application/validation/)) - zod request schemas plus the shared `validate()` helper. Schemas describe request shape only: types, required scalars, formats, ranges, and array item shape. Domain invariants stay in entities, so each rule lives in one layer only.
- **Use cases** ([backend/src/application/use-cases/](backend/src/application/use-cases/)) - one class per operation with `async execute(...)`. They hold input validation + orchestration, throw domain errors, and depend on repository/service TypeScript `interface`s, never on `pg` or express. Service ports are in [backend/src/application/ports/](backend/src/application/ports/) (`PasswordHasher`, `TokenService`).
- **Domain** ([backend/src/domain/](backend/src/domain/)) - repository TypeScript `interface`s, entities, and error types in [backend/src/domain/errors/AppError.ts](backend/src/domain/errors/AppError.ts) (`AppError` carries a `code`, an HTTP `status` and an optional `detail`; `ValidationError`/`UnauthorizedError`/`ForbiddenError`/`NotFoundError`/`ConflictError`).
  `Recipe` and `Menu` entities keep domain invariants such as non-empty ingredients/recipes and required menu category.
- **Infrastructure** ([backend/src/infrastructure/](backend/src/infrastructure/)) - concrete `pg` repositories under `persistence/pg/` (ALL SQL lives here) and security adapters under `security/` (`BcryptPasswordHasher`, `JwtTokenService`). Adapters `implements` the relevant interface and each repository takes the shared `pool` from [backend/src/db.ts](backend/src/db.ts) via its constructor.
- **Config and ambient types**: [backend/src/config/env.ts](backend/src/config/env.ts) is the single typed environment loader, and [backend/src/config/logger.ts](backend/src/config/logger.ts) is the shared pino logger (`LOG_LEVEL`, silent in tests). [backend/src/types/](backend/src/types/) is only for ambient `.d.ts` declarations such as `express.d.ts` and `env.d.ts`; regular DTO/domain types live beside their layer as normal `.ts` exports.

Errors: a use case `throw`s a domain error; Express 5 forwards the rejected promise to the single `errorHandler` ([backend/src/middleware/errorHandler.ts](backend/src/middleware/errorHandler.ts)), which logs through pino (a 4xx as one compact `warn` line with no stack, a 5xx in full at `error`) and replies `{ error, code }` with `err.status || 500`. Nothing else writes an error response: auth middleware failures, rate-limit rejections and the JSON 404 for unknown routes all call `next(error)`, so every error body has the same shape.

**Error codes are the contract; display text lives in the catalog.** Every client-facing error is an `AppError` built from a code in [backend/src/constants/errorCodes.ts](backend/src/constants/errorCodes.ts) (`ERROR_CODES`, namespaced by domain: `recipe/not_found`, `auth/session_expired`) - never from a message string. `AppError` holds no display text: `errorHandler` resolves it at the HTTP edge as `detail ?? translateError(code, locale)`. All server-side copy lives in JSON catalogs under [backend/src/i18n/locales/](backend/src/i18n/locales/) (`errors.json` keyed by code, `messages.json` for `{ message }` success bodies via `translateMessage`, `email.json` via `getEmailCopy`) behind [backend/src/i18n/translate.ts](backend/src/i18n/translate.ts), whose `satisfies Catalog` makes a key missing from any locale a compile error. A new error = one `ERROR_CODES` entry + one line in every locale's `errors.json` + the same entry in `frontend/src/constants/errorCodes.ts` (a backend test fails if that mirror drifts in either direction) + its user-facing copy under `apiErrors` in every frontend `common.json` (a frontend test fails if a code has none in English, and the completeness test if any other language lacks it). The frontend renders error text from that copy by code - `getApiErrorMessage` falls back to the server's English `error` only for a code the build doesn't know. **Server copy has two locale sources, and every translate call takes one explicitly** (no default argument, so nothing silently falls back to English): a response follows the request through `requestLocale(req)` (`Accept-Language` matched against `LOCALES` in `constants/locales.ts`, else `en` - the frontend's `apiClient` sends the language the app is showing), and an email follows the recipient's stored `person.locale` (set from the request's language at registration, changed through `PUT /me/locale`), because it is read long after the request. The server speaks `en`, `pl`, `ru` and `uk`, the same list as the frontend's (`constants/__tests__/locales.test.ts` compares them). A new locale = one `LOCALES` entry + one `locales/<locale>/` folder + one `CATALOGS` entry; `satisfies Record<Locale, Catalog>` makes a missing one a compile error. Email links point at the page in the recipient's language (`emailLink`), and the email's HTML carries its `lang`. Misconfiguration or programming failures (missing JWT secret, a route without `req.user`) are plain `Error`s, not `AppError`s - every 5xx answers `server_error` and never leaks its message.

When adding a feature: add SQL to the relevant `Pg*Repository` (and its interface), add a zod schema in `application/validation/`, add a use case (which calls `validate(...)` then orchestrates), call it from a controller handler, and wire the new pieces in the composition root. Transactions (`BEGIN/COMMIT/ROLLBACK`) live inside a single repository method (see the menu/pantry repos).

Search/filter SQL is assembled by [`SqlFilterBuilder`](backend/src/infrastructure/persistence/pg/sqlFilterBuilder.ts), never by hand. Each filter is one entry in a clause registry (`recipeFilterClauses.ts` / `menuFilterClauses.ts`) declaring `applies` and `apply`; the builder hands out `$n` placeholders through a `bind()` callback, so indices can't drift from the values array - the hand-rolled `paramIndex` counter it replaced had exactly that bug. Anything interpolated into an `ILIKE` pattern goes through `escapeLikePattern()` first, so a literal `%` or `_` in user input stays literal. Adding a filter = one clause entry + one zod field, with no change to query assembly. Note that `apply` re-tests the condition `applies` already gated on: `applies` is a plain predicate, so TypeScript can't narrow through it - the repetition is what lets `apply` use the field without a cast.

Auth flow: auth is an httpOnly cookie (`authToken`), not a Bearer header. `POST /login` signs an HS256 JWT with payload `{ id, typ: "session", sv }` and `expiresIn: "24h"` via [backend/src/infrastructure/security/JwtTokenService.ts](backend/src/infrastructure/security/JwtTokenService.ts), then sets it as a cookie (`res.cookie(AUTH_COOKIE_NAME, token, AUTH_COOKIE_OPTIONS)` from [backend/src/config/cookie.ts](backend/src/config/cookie.ts)) and responds `{ message: "Logged in" }` - the token is never in the body. [backend/src/middleware/jwtMiddleware.ts](backend/src/middleware/jwtMiddleware.ts) reads the token from `req.cookies[AUTH_COOKIE_NAME]` (401 if missing, 403 if invalid), verifies it, checks its session version against the database, and attaches `req.user`. `GET /me` returns the current user (including `email`, `email_verified_at`); `POST /logout` (public) clears the cookie. The current user's id always comes from `req.user.id` via the `getUserId(req)` helper ([backend/src/controller/requestUser.ts](backend/src/controller/requestUser.ts)), never from the request body/params.

Registration requires a unique `email` alongside `login` (both enforced by DB unique constraints, with distinct `409` error codes). Every error response carries its stable `code` (see the error-code paragraph above), so the frontend shows the exact right copy per cause instead of guessing from the HTTP status. Password reset (`POST /forgot-password` + `POST /reset-password`) and email verification (`PUT /email`, `POST /resend-verification-email`, `POST /confirm-email`) reuse the session JWT's signing mechanism as short-lived purpose-scoped tokens (`TokenService.generatePurposeToken`/`verifyPurposeToken`, a `purpose` claim); password-reset tokens are additionally bound to a fingerprint of the password hash at issue time, so a link stops verifying the moment it's used once.

**Token separation is enforced in both directions, and both halves are load-bearing.** Purpose tokens are signed with the same `JWT_SECRET_KEY` as sessions, so each side must identify itself positively: `verifyPurposeToken` requires `purpose` to match, and `jwtMiddleware.isSessionPayload` requires `typ === SESSION_TOKEN_TYPE` ([backend/src/config/security.ts](backend/src/config/security.ts)). Do NOT relax the middleware to "any well-formed `{ id }`" - that would let an emailed reset/verify link be pasted in as an `authToken` cookie and act as a full session for its whole TTL (24h for verify-email, which carries no hash binding). Pinned by tests in `middleware/__tests__/jwtMiddleware.test.ts`. Reset is gated on a verified email and always returns the same generic response regardless of whether the email exists or is verified (anti-enumeration). Anti-enumeration also covers response _time_: `LoginUser` runs `passwordHasher.compare` against `LOGIN_TIMING_DECOY_HASH` when the account doesn't exist, so an unknown login costs the same ~60ms of bcrypt as a wrong password - returning early there would leak which logins are real regardless of the identical error body. `POST /change-password` checks the current password and is excluded from the frontend's global "401 → redirect to /login" interceptor, since a wrong-current-password 401 there is a normal in-band form error, not an expired session. Full detail in [backend/README.md](backend/README.md#auth-flow).

**A password change ends every other session.** `person.session_version` is sealed into each session token as `sv`; `updatePassword` raises it (a change and a reset alike), and the middleware rejects any token whose `sv` no longer matches - a stolen cookie dies with the old password instead of living out its 24 hours. `POST /change-password` answers with a fresh cookie under the new version, so the session that made the change stays signed in. The check costs one primary-key read per authenticated request; a deleted account (`null` version) fails it too. The two middlewares come from one factory, `createSessionAuth(userRepository)`, built in the composition root and handed to every router as its last argument (`{ authenticateToken, optionalAuth }: SessionAuth`) - a router never imports them directly.

### Frontend - api layer, routing, auth

**Auth is an httpOnly cookie, not localStorage.** The client never reads or stores a token. The shared axios instance [frontend/src/api/client.ts](frontend/src/api/client.ts) is created with `withCredentials: true`, so the browser carries the `authToken` cookie automatically - there is no `Authorization` header anywhere. `PrivateRoute` ([frontend/src/components/layout/PrivateRoute/PrivateRoute.tsx](frontend/src/components/layout/PrivateRoute/PrivateRoute.tsx)) gates by calling `getMe()` (`GET /api/me`) on mount: 200 renders the route, 401/403 redirects to `/login`, other errors show a session error. The api client's single response interceptor (`handleAuthError`) also hard-redirects to `/login` on a 401/403 for any protected request (except `/api/me`, `/api/change-password` - a 401 there means "wrong current password", not an expired session - and the public paths).

**All HTTP goes through the `api/` layer - never import `axios` in a page, hook, or component** (an `eslint-plugin-boundaries` rule blocks it). [frontend/src/api/](frontend/src/api/) holds the shared `client.ts`, `endpoints.ts` (the typed `API_ROUTES` map; parameterized routes are builders), `httpError.ts` (`getApiErrorMessage`/`getApiErrorCode`/`getApiErrorStatus`/`getApiErrorRetryAfter` - normalize any error from the backend's `{ error, code }` body; the message is the app's own `apiErrors.<code>` copy when the code is known), and `redirect.ts`. It is transport-only - there is no per-domain wrapper here; those live one layer up, in `redux/services/` (see below).

Routing is the folder tree under [frontend/src/app/](frontend/src/app/). **Every page lives under `app/[locale]/`, and the URL is the one source of the page's language**: English, the default, is served without a prefix (`/recipe/42`), the others with one (`/pl/...`, `/ru/...`, `/uk/...`). [frontend/src/proxy.ts](frontend/src/proxy.ts) is a thin wrapper over the pure `resolveLocaleRoute` ([frontend/src/utils/localeRouting.ts](frontend/src/utils/localeRouting.ts)): a prefixed path passes, `/en/...` answers a 308 to the bare path, and a bare path is rewritten to `/en/...` unless the visitor's saved choice (the `NEXT_LOCALE` cookie) or else their `Accept-Language` asks for another language, which is a 307 to its prefix. Crawlers are never redirected, so every language version stays reachable to them. `[locale]/layout.tsx` is the root layout (`<html lang>`, a `notFound()` for an unknown language), and `[locale]/[...missing]/page.tsx` catches any address no route claims so the 404 renders inside it; `sitemap.ts`, `robots.ts` and `health/route.ts` stay outside the segment, as do `providers.tsx`, `themeInit.ts` and `socialImage.tsx`, which are not routes. The language list is `LOCALES` in [frontend/src/constants/locales.ts](frontend/src/constants/locales.ts); `utils/localePath.ts` (`localizePath`, `stripLocale`) is the only place a prefix is added or removed. Three route groups carry the whole map and never appear in a URL: `(auth)` for the sign-in pages, `(public)` for everything a guest may read, and `(private)`, whose `layout.tsx` is a single `PrivateRoute` wrapper - **a page is private because of where it lives, so it cannot forget its own guard**. **`page.tsx` is the page** - the component lives there, with its own stylesheet and its co-located `__tests__/`, so a route is one folder and there is no parallel tree mirroring it. The five public read pages - `/`, both listings, both detail pages - are server components: `page.tsx` fetches and renders, and the interactive half sits beside it as a client island (`RecipeDetailsView`, `AllRecipesView`, ...) that receives its data as props rather than fetching it again. The root `layout.tsx` owns `<html>`/`<body>` and the providers; `error.tsx` and `not-found.tsx` replace the old router-level error and 404 elements. **`loading.tsx` sits in the client-rendered groups (`(auth)`, `(private)`, both listings), never at the root** - it is the Suspense boundary those pages need to read search params, but a boundary above a server-rendered page flushes the response before that page has decided, and the status can no longer be changed once bytes are out. `constants/routes.ts` is no longer the router's source of truth but is still the only place a path may be written: its builders produce every link, and `PUBLIC_PATHS` feeds `matchRoutePattern` in the api layer. **The app has exactly one `route.ts`** - `app/health/route.ts`, the container's liveness probe. Everything the product itself serves over HTTP belongs to the backend and is reached through the `api/` layer; do not add a second route handler to move application logic into the frontend process.

**Uploaded images are the one attack surface a file brings, and every step of the pipeline is load-bearing.** The upload routes read the body with `express.raw` (mounted on those routes only, after auth and a per-user limiter; `express.json` stays the only app-wide parser); the bytes are sniffed for a JPEG/PNG/WebP/AVIF signature (SVG is refused - it is a script container served from a domain that shares the session cookie); `sharp` then decodes and **re-encodes** every upload into fixed renditions - WebP at 400 and 1200 px plus a 1200x630 JPEG for link previews (`IMAGE_VARIANTS` in `application/media/mediaFiles.ts`; `limitInputPixels`, `failOn: "truncated"`, EXIF stripped, orientation applied) and the original bytes are discarded - that step, not the sniff, is what kills polyglots, decompression bombs and GPS leakage. Files are named by a server-generated UUID and written before the database points at them. `GET /media/:file` accepts only those exact name shapes and answers the type its own rendition names (`image/webp` or `image/jpeg`, never read from the request), `nosniff`, `Content-Disposition: inline`, an immutable cache and `Cross-Origin-Resource-Policy: same-site` - helmet's default `same-origin` would stop the app domain from loading an image off the API domain, and only a browser shows that, never `curl`. Do not drop any of these as redundant.

**The app domain sends its own security headers** from `next.config.ts` (`SECURITY_HEADERS`): a CSP limited to `frame-ancestors`, `object-src`, `base-uri`, `form-action` and an `img-src` that allowlists the API origin (photos are served from there), plus `X-Frame-Options`, `nosniff`, `Referrer-Policy` and `Permissions-Policy`. There is deliberately no `script-src` yet - a nonce-based one needs a middleware this app does not have. A new image host has to join `img-src`, or every image from it silently fails to load.

**Server-side requests go through [frontend/src/api/server.ts](frontend/src/api/server.ts), never a bare `fetch`.** `fetchAsVisitor` carries the visitor's **session cookie only** (`AUTH_COOKIE_NAME`, nothing else the browser holds for the origin), `x-forwarded-for`, and the page's language as `Accept-Language` into the API, and is always `no-store` - a response assembled for one session must never be reused for another, which is the worst thing that can go wrong in a server-rendered app. `fetchPublic` carries no session and may be cached; the sitemap is its only caller. The cookie is forwarded, never parsed - `jwtMiddleware` stays the single place a token is verified. Both requests have a deadline, because a hung API would otherwise pile up renders until the frontend container fails its own health check. The module imports `server-only`, so pulling it into a client component is a build error rather than a silent leak.

**Metadata is per route.** Every public page owns its `generateMetadata` (title, description, alternates, OG) - the root layout deliberately sets no canonical, and the two list pages canonicalize every filtered permutation back to the clean URL. Alternates come from `pageAlternates(path, locale)`: each language version is its own canonical and lists the others as `hreflang` alternates, with the bare English path as `x-default`; `socialMetadata` takes the same path and locale for `og:url`, `og:locale` and the alternate locales. A record that does not exist answers a real HTTP 404. That takes two things together, and neither works alone: `htmlLimitedBots: /.*/` in `next.config.ts`, so Next waits for `generateMetadata` instead of streaming it in later, and no `loading.tsx` above the route. Both are load-bearing - putting a Suspense boundary back at the root turns every missing recipe into a 200. [frontend/src/app/sitemap.ts](frontend/src/app/sitemap.ts) walks the public paginated endpoints and lists public URLs only, each page once per language with the others as alternates (it is built per request - the image is built where the API is unreachable), [frontend/src/app/robots.ts](frontend/src/app/robots.ts) disallows the private prefixes derived from `constants/routes.ts` in every language, and the `(private)` layout carries one `noindex` for the whole group. `/` is the one page whose content depends on the session: it is decided on the server, and when the API does not answer the decision falls back to the client-side `HomeRoute` gate rather than defaulting a signed-in visitor to the landing page.

**Link previews and structured data.** Each public route has an `opengraph-image.tsx` rendering a 1200x630 card through `next/og` (`SocialCard`, drawn by `app/socialImage.tsx`, which loads the brand fonts once - Inter covers the Cyrillic Fraunces lacks); the two listings re-export the root one. A recipe or menu with a photo previews as that photo instead: its page sets `openGraph.images` to the server's JPEG rendition through `socialMetadata`/`photoSocialImage`, and a page's own images win over the file-based card. Three things here are easy to break: every page that sets `openGraph` must go through `socialMetadata` (a child's `openGraph` replaces the parent's wholesale, dropping the large card type), the `images` key must be left out rather than set to `undefined` (an undefined one wipes the generated card), and `generateImageMetadata` must not fetch - Next also calls it as `generateStaticParams`, where reading the session cookie throws, which is why the card is declared unconditionally. The renderer calls every component as a plain function, so a card can use only inline styles and server-safe components - a `lucide-react` icon (a client component) makes it 500. The detail pages also carry `schema.org` JSON-LD (`Recipe`, and an `ItemList` of recipe pages for a menu) through `components/seo/JsonLd`, which escapes `<` so a title cannot close the script tag.

**Navigation goes through two wrappers, and ESLint blocks the alternatives.** Links use `Link` from `components/ui/Link`, programmatic navigation uses `useAppRouter` from `hooks/useAppRouter`; importing `next/link`, or `useRouter` from `next/navigation`, is a lint error outside those two files. Both route through `NavigationBlockerProvider` ([frontend/src/components/layout/NavigationBlocker/](frontend/src/components/layout/NavigationBlocker/)), the app's own answer to a framework that has no navigation guard: a form with unsaved edits registers a dirty ref through `useUnsavedChangesBlocker`, and the provider intercepts link clicks, programmatic pushes, tab close (`beforeunload`) and the back button (a duplicate history entry it pushes while a guarded form is mounted, since a browser pop cannot be cancelled after the fact). A bare `next/link` would render a working link with no guard at all, and nothing at the call site would show it - hence the lint rule.

**A server-rendered page is on screen before React hydrates.** Anything that would behave differently in that window has to say so: `useIsHydrated` ([frontend/src/hooks/useIsHydrated.ts](frontend/src/hooks/useIsHydrated.ts)) is false for the server render and the first client render and true from the next one on, which is how `useLoginLockout` reads its stored state without a hydration mismatch. `Button` uses it too: a `type="submit"` button stays disabled until hydration, because a submit landing before then is a native browser submit that would put every field - passwords included - into the URL. Since the public pages started arriving fully rendered, the same gate covers **any** control whose only behaviour is a click handler: `Button` disables itself whenever it carries an `onClick`, and the hand-rolled action buttons (`OwnerActions`, `MenuHeroActions`, `ThemeToggle`, the account-menu trigger) do it with `useIsHydrated` directly. A press that lands before hydration is swallowed without a trace, so a button must not look ready while it is not.

**Per-viewer state on a server-rendered page comes from the record, not the session.** Search and detail responses carry `isOwner`, `isFavourite`, `containsAvoided`, `tags` and `myRating` computed for the requester, and `isFavourite`, `containsAvoided` and `tags` are `null` exactly when the request had no session (`myRating` is also `null` for a viewer who hasn't voted, so it cannot tell a guest apart). A page decides its guest branch from that (`isFavourite === null`) - the client `session` slice is still `checking` during the first paint, and reading it there flashed the "Log in for the full experience" CTA at signed-in visitors. Client-only UI with no record to read (filter popovers) keeps using `selectViewerCapabilities`. The shopping list is the one list patched optimistically in the RTK Query cache itself (`onQueryStarted` + `updateQueryData` in `shoppingListApi`): a tick or a reorder shows at once and is undone if the request fails, and both still invalidate the list, so the refetch after the write replaces whatever an overlapping refetch brought back from before it. Its rows and cards glide to their new places through `useFlipAnimation` (FLIP on the Web Animations API, keyed by `data-flip-id`, skips elements that are not laid out and honours reduced motion itself, since the global CSS rule does not reach WAAPI) - reuse it for any other list that reorders. Other pages put catalog ingredients on the list through `useAddToShoppingList`, whose success toast carries a link to the list (a toast's optional `link`). The heart is `FavouriteButton` driven by `useFavouriteToggle` (optimistic, rolls back on failure, disabled until hydrated); it invalidates the record's tag plus its `LIST` tag, so a favourites-filtered list picks up a newly added item. `ContentCard` is an `<article>` whose title link is stretched over the whole card with `::after`; the heart sits above it as a sibling button - never put a button inside the card link, which is invalid markup and turns the press into a navigation.

State lives in custom hooks under [frontend/src/hooks/](frontend/src/hooks/) (50+, composed) and in a Redux Toolkit store under [frontend/src/redux/](frontend/src/redux/). The store is wired in [frontend/src/redux/store.ts](frontend/src/redux/store.ts) via a `setupStore` factory shared by the app and tests; typed hooks (`useAppDispatch`, `useAppSelector`) live in [frontend/src/redux/hooks.ts](frontend/src/redux/hooks.ts). Server data is cached with **RTK Query**: a single `baseApi` ([frontend/src/redux/services/baseApi.ts](frontend/src/redux/services/baseApi.ts)) built on a custom `axiosBaseQuery` that routes every request through the shared `apiClient` (never `fetch`, so the auth cookie + 401/403 interceptor still apply), with one injected endpoint file per domain under [frontend/src/redux/services/](frontend/src/redux/services/) (`recipesApi`, `menusApi`, `authApi`, ...) exporting `useGet*Query`/`use*Mutation` hooks; cache invalidation runs off `tagTypes` (a mutation invalidates the tags its queries provide, so lists refetch automatically). Data flow: page/hook → RTK Query hook (`redux/services`) → `axiosBaseQuery` → `api/client`. **Invalidate across domains whenever the backend cascades**: a mutation must invalidate every tag type its write touches server-side, not just its own - deleting a recipe also invalidates `Menu` (the delete cascades into `menu_recipe`, changing menu contents and recipe counts), and pantry writes invalidate `Recipe/LIST` (the `in_pantry` filter's results change). Missing one leaves a stale screen that only fixes itself after `keepUnusedDataFor` expires. Client/UI state lives in slices under `redux/slices/<domain>Slice.ts` (`session`, the `ui` modal queue, `notifications` toasts); each slice's selectors always live in a separate `redux/selectors/<domain>Selectors.ts` - never inline in the slice or in components.

**Every modal goes through the one FIFO queue in `uiSlice` (`ui.queue`), and `ModalRoot` is the only place a modal renders.** Never mount a modal in place from a page or component - dispatch `openModal({ type, ...payload })` and let `ModalRoot` render the head of the queue, so a second modal waits instead of stacking on or clobbering the first. `openModal` ignores a type already queued (a second modal of the same type is always an accidental double dispatch, since the first covers the screen). A modal closes itself with `closeModal(modalId)`. State-driven modals get a hook that owns the lifecycle (`useOfflineNotice`), not local component state, and any "shown once" marker is written when the modal is actually presented, not when it is enqueued - otherwise a notice still waiting its turn is recorded as seen and never returns. Toasts stay a deliberately separate queue (`notificationsSlice`, several visible at once, non-blocking); do not merge the two. Full detail in [frontend/README.md](frontend/README.md#modals---one-queue-one-renderer). For no-argument endpoints and empty mutation responses use `null`, not `void` (the strict lint config rejects `void` in call type-arguments). User-facing strings go through i18next ([frontend/src/i18n/](frontend/src/i18n/), one namespace per domain) via `useTranslation`. Bare path aliases (`api/`, `app/`, `hooks/`, `components/`, `types/`, `utils/`, `constants/`, `config/`, `i18n/`, `redux/`, `assets/`, `styles/`, `test/`) - never `../` across folders. A stylesheet shared by several routes sits in their common group folder and is imported through the `app/` alias, since `../` is not available.

**Search and filtering go through one declarative framework - never hand-roll a filter.** Each list declares a registry of filter descriptors ([frontend/src/utils/filters/](frontend/src/utils/filters/): `recipeFilterDefs.ts`, `menuFilterDefs.ts`, built from the `textFilter`/`idListFilter`/`numericRangeFilter`/`booleanFilter`/`enumFilter` factories), and everything derived - request params, the active-filter chips, the badge count, reset - comes out of that one registry via `filterState.ts`. Two hooks consume it: `useListFilters` (URL-backed, for the server-side recipe/menu lists - the URL is the single source of truth, which is what makes a filtered view shareable) and `useClientFilters` (local state, for client-filtered lists like the pantry). Adding a filter should be one registry entry plus one control, nothing else.

Three rules the framework depends on:

- **Write multiple filter keys with `setValues`, not repeated `setValue`.** Each `setValue` closes over the same `searchParams` from its render, so N sequential calls in one handler all read pre-update state and only the last survives. Pinned by a test in `hooks/__tests__/useListFilters.test.ts`.
- **Free-text inputs are debounced and write with `{ replace: true }`.** `SearchField` and the cooking-time range fields (via `useDebouncedFieldSync`) commit ~300ms after typing stops; without `replace` every keystroke would push its own history entry and fire its own request.
- **A reset that leaves a debounced field's committed value unchanged must remount it.** The field syncs from its `value` prop, so clearing a field that was already `""` produces no prop change - a still-pending edit would commit right after the reset and silently re-apply what the user just cleared. Callers bump a `key` (`searchResetKey` / `popoverResetKey` in `RecipeListView`/`RecipeFilterPanel`) instead of relying on the prop.

Page components live in their own route folder under [frontend/src/app/](frontend/src/app/), as `page.tsx`, next to the client island a server page renders. Reusable UI lives in [frontend/src/components/](frontend/src/components/), grouped by domain plus `layout/`, `ui/`, and `icons/`. The stats page renders its charts with `recharts` (lazy-loaded page chunk); PDF export was removed in 3.3. Recipe types are reference data behind a read-only API - there is no recipe-types page or component folder (the CRUD page was removed in 1.40).

### Database model highlights

Key tables and joins (see the initial migration [backend/migrations/1781185648364_initial-schema.sql](backend/migrations/1781185648364_initial-schema.sql) for the full schema):

- `person` (users) <-> `recipes` via `person_id`
- `recipes` <-> `ingredients` through `recipe_ingredients` (with `quantity_recipe_ingredients`)
- `recipes.type_id` -> `recipe_types`
- `person` <-> `ingredients` through `person_ingredients` (the pantry, with `quantity_person_ingradient` - note the misspelling, it's the actual column name) and `ingredient_purchases` (history)
- `menu` (per-user, with `category_id` -> `menu_category`) <-> `recipes` through `menu_recipe`
- `recipe_favourites` / `menu_favourites` (person <-> recipe / menu, composite primary key) - every foreign key is `ON DELETE CASCADE`, because recipe, menu and account deletion are hand-written transactions that know nothing about favourites. Search and detail queries add a per-requester `isFavourite` column (`isFavouriteColumn`, `null` for an anonymous requester) next to `isOwner`, and the `favourites=true` filter is one shared clause (`favouritesFilterClause`) in both registries
- `shopping_list_items` (per-user, optional `ingredient_id` -> `ingredients` with `ON DELETE SET NULL` plus `quantity`) - writes run in one transaction that locks the owner's `person` row, so the item limit and `position` can't race; adding an ingredient merges into its unchecked item (the quantities add up, a `null` one leaves the other as is) instead of duplicating it
- `person_avoided_allergens` / `person_avoided_ingredients` (the viewer's avoid list, `ON DELETE CASCADE`) - search and detail queries add a per-requester `containsAvoided` column (`containsAvoidedColumn`, `null` for a guest); without an explicit `sort_order` a signed-in list ranks favourites first and avoided recipes last, and `hide_avoided`/`exclude_allergens` are clauses in `dietFilterClauses.ts`. The avoid list is edited optimistically in `dietPreferencesApi` (every write also invalidates `Recipe`), and pages that already hold ingredients mark avoided ones through `useAvoidedIngredients`
- `person_tags` / `recipe_tag_links` (the viewer's private tags, `ON DELETE CASCADE`, unique on `(person_id, lower(name))`) - search and detail queries add a per-requester `tags` column (`recipeTagsColumn`, `null` for a guest) and `tag_ids` filters on it. A tag goes on any recipe the viewer can see; the recipe page keeps the assignment in `useRecipeTags`, since the page itself is server-rendered
- `recipes.photo_key` / `menu.photo_key` / `person.avatar_photo_key` (nullable UUIDs naming stored files) - `person.avatar` keeps the preset key beside the photo, so removing the photo brings the preset back. Search and detail queries add an `author` object (`authorColumn`: first name, surname initial, avatar and photo - never login or email). Recipe, menu and account deletion return the photo keys they removed (`DELETE ... RETURNING`, under the row lock the delete already takes) and hand them to `PhotoCleanup` after the write commits - reading the keys in a separate query first let an upload landing in between orphan its files on disk
- `recipe_ratings` / `menu_ratings` (one vote per person and record, `value` 1-5, `ON DELETE CASCADE`) - `recipes`/`menu` keep running `rating_sum`/`rating_count` totals maintained by an `AFTER` trigger on the vote tables, the one trigger in the schema: an account deletion cascades its votes away, and only a trigger sees that, so do not move the arithmetic into repository code. The average is computed on read (`ratingColumns.ts`: `ratingAverage`, `ratingCount`, per-requester `myRating`), `top_rated` is a shared clause in both registries and `sort_order=rating` ranks by a Bayesian average (`RATING_SORT_PRIOR`). The frontend's `useRatingControl` is optimistic like `useFavouriteToggle` and also shifts the average locally, since a server-rendered detail page has no cache entry to refetch
- `ingredients` carries `id_unit_measurement` -> `unit_measurement` plus metadata (`allergens`, `days_to_expire`, `seasonality`, `storage_condition`)

The "missing ingredients for a menu" feature works by joining `menu_recipe` -> `recipe_ingredients` -> `ingredients` and subtracting the user's `person_ingredients`.

## Conventions in this codebase

- **i18n is mandatory for every user-visible string in the frontend.** Never hardcode English (or any other language) text in components, hooks, or Redux middleware. Add every new string to the appropriate JSON file under `frontend/src/i18n/locales/en/` (`common.json` for cross-cutting messages like toasts and generic errors; domain namespaces for domain-specific text) and to the same file under `pl/`, `ru/` and `uk/` - `i18n/__tests__/localeCompleteness.test.ts` fails otherwise. Recipe types, menu categories and units are never printed from the record: `utils/referenceLabels.ts` translates them, and `quantityWithUnit` writes an amount with its unit in the page's language.
- **Nothing that renders touches the global `i18next` instance.** The server renders requests in different languages side by side, so each gets its own instance (`createAppI18n` in `providers.tsx`; `getServerTranslation(locale, namespace)` for metadata and preview images, which always takes the locale explicitly). In components and hooks use `useTranslation("namespace")`, and `useLocale()` for the page's language. A helper that translates or formats takes what it needs as arguments - `resolveIngredientName(t, ingredient)`, `formatKcal(value, locale)`, `formatShortDate(date, locale)` - and never reaches for `i18next` or a fixed `"en-US"` itself; `utils/intlFormat.ts` caches the `Intl` formatters. The global instance is the browser's own (one visitor, one language) and is only for code that runs outside React on the client: the Redux middleware toasts, `api/httpError.ts`, and the `Accept-Language` interceptor in `api/client.ts`. The browser receives only its own language's strings (`RESOURCES[locale]`, handed down by the layout); `i18n/resources.ts` is `server-only`, so importing it into a client component fails the build instead of shipping every language.

- **Hand-authored SVG icons are always their own React component, never an inline `<svg>` copy-pasted into a page/component.** This is only for custom marks that don't come from `lucide-react` (e.g. the Donburi brand mark) - Lucide icons are already components and are imported directly. Shared hand-authored icons live in `frontend/src/components/icons/`, one component per file, typed with a shared `{ size?: number; className?: string }` props shape, themed via `stroke="currentColor"` so they inherit the surrounding text color. If an icon has size-dependent detail tiers (see `components/icons/DonburiMark*.tsx` for the pattern), give each tier its own component rather than branching SVG path data inside one component.
- **New icons match the existing set, they don't approximate it.** Prefer a `lucide-react` icon when one genuinely fits; hand-author a component only when nothing in Lucide matches the concept. If design mockups are available for the screen (they live outside the repo - ask), trace their exact `<path>`/`<rect>`/`<circle>` data rather than substituting a stock icon that merely "looks close enough".

- **Docs live with the code and must not drift.** The docs describing how the app works are [README.md](README.md) (project overview), this file (agent-facing conventions and architecture), [backend/README.md](backend/README.md), and [frontend/README.md](frontend/README.md). When a change makes any statement in them wrong or incomplete - a new middleware, a changed API contract, a new env var or script, a removed page, a new architectural rule - update the affected doc in the SAME commit as the change. Only the docs the change actually touches; don't churn all four every release. A brand-new doc is warranted only when a real subject has no home at all, and it must be linked from the doc that should have covered it, so it stays discoverable.

- **Every UI change must be responsive and verified at the app's breakpoints, not desktop only.** Match the existing SCSS breakpoint patterns the redesign uses everywhere (desktop 1280, tablet portrait/landscape, mobile portrait/landscape). Before claiming any UI work done, check it live (Playwright/preview screenshots) at minimum on mobile portrait + desktop, plus tablet whenever the layout differs there - broken layout at non-desktop widths is the most common regression, "it renders on desktop" is not done.

- Comments are a last resort: the default is NO comment; write one only for a genuinely non-obvious "why", and keep it to a few words on one line - never a sentence explaining the change. Style: plain `//` with a single space and a lowercase first letter (acronyms / proper nouns like JWT, SQL, URL, Express keep their case, e.g. `// JWT login`). Never use `//?` / `//!` prefixes.
- Backend source is TypeScript with ESM-style `import`/`export`, executed by `tsx` with CommonJS runtime semantics (`module: "CommonJS"` in [backend/tsconfig.json](backend/tsconfig.json)). Do not add new `require`/`module.exports` in backend source files; root tooling configs such as ESLint and Jest stay CommonJS `.js`.
- Backend layering rules (keep the style uniform):
    - In a controller, every injected use case is a field named `<operation>UseCase` (e.g. `this.createRecipeUseCase`), called from the matching arrow-function handler. Uniform naming, and it never clashes with a handler name.
    - Add a `domain/entities/` class only when it enforces an invariant. The write use case builds it through a named factory (`Recipe.forCreation(...)` / `Recipe.forUpdate(...)`) that throws a `ValidationError`, then passes the entity to the repository. Do NOT create empty data-holder entities, and do NOT route reads through entities (queries return repository rows as-is, so response shapes stay identical).
    - Validate request input with a zod schema in `application/validation/` (one `<area>.schemas.ts` per domain, shared field helpers in `common.schemas.ts`); the use case calls `validate(schema, input)` from [backend/src/application/validation/validate.ts](backend/src/application/validation/validate.ts) at the top of `execute()` before building any entity. Schemas cover request shape only (types, required scalars, formats, ranges, array item shape) - the entity factory keeps the domain invariant (e.g. non-empty ingredients), so each rule lives in exactly one layer and zod does NOT duplicate it. A failed `validate` throws `ValidationError` (400), so every bad input is `{ error }`.
    - One route path = exactly one handler. Don't register a second router on a path another router already owns - the later one is unreachable dead code (mount order is in [backend/src/routes/domainRouters.ts](backend/src/routes/domainRouters.ts)).
    - A client-supplied foreign key must be checked in the use case, not left to Postgres. zod validates shape only, so an id that is well-formed but nonexistent reaches the `INSERT`, and the FK violation surfaces as a bare 500 (it carries no `status`). Every write that accepts ingredient ids calls `assertIngredientsExist` ([backend/src/application/validation/assertIngredientsExist.ts](backend/src/application/validation/assertIngredientsExist.ts)) first, turning it into a 400 - recipes and both pantry use cases all do this.
    - All SQL lives in `infrastructure/persistence/pg/*` repositories that implement an interface from `domain/repositories/`; multi-step transactions (`BEGIN/COMMIT/ROLLBACK`) stay inside a single repository method.
    - Type placement follows the layer: use inline types for one file, co-located `<area>.types.ts` for shared DTO/filter shapes inside a folder, and exported entity/repository types from their own modules. Do not turn `backend/src/types/` into a general type bucket.
- Backend path aliases are configured in [backend/tsconfig.json](backend/tsconfig.json) via `paths` only (no `baseUrl` - it is deprecated in TypeScript 6): bare-form folder aliases `domain/*`, `application/*`, `infrastructure/*`, `controller/*`, `routes/*`, `middleware/*`, `config/*`, `constants/*`, `i18n/*`, `scripts/*`, `test/*`, plus singleton aliases `app` and `composition-root` for the two top-level modules. Do not introduce `../` imports under `backend/src/`; cross-folder imports use bare aliases, same-folder neighbors stay relative with `./`. `tsx` resolves `paths` at runtime, tsup/esbuild resolves them at build time, and Jest maps them via an explicit `moduleNameMapper` in [backend/jest.config.js](backend/jest.config.js) (no dynamic tsconfig read).
- The DB column `quantity_person_ingradient` keeps its misspelling on purpose (it is the real column name) and appears verbatim in API responses - do not "fix" it. The frontend folder is spelled correctly (`person-ingredients`); only the column is misspelled.
- `backend/package.json` pins tsup's nested esbuild via an `overrides` entry (tsup's own range allowed a vulnerable version - GHSA-g7r4-m6w7-qqqr). When bumping tsup, check whether its esbuild range is fixed and drop the override.
- All three `package.json` files pin `brace-expansion` per major line (`brace-expansion@1`/`@2`/`@3`) to the backported releases that fix GHSA-mh99-v99m-4gvg. `npm audit` used to report these as vulnerable even though the fixed backports (`1.1.18`/`2.1.4`/`3.0.6`) were already installed - a false positive from the advisory's affected range being written `<=5.0.7`, which numerically covered them. As of 4.2 the advisory range has been corrected upstream and audit is clean; the overrides stay in place since they still pin the right versions. Do NOT "fix" this with a blanket `"brace-expansion": "^5"` override - 5.x switched to a named export and old `minimatch@3` does `require("brace-expansion")` expecting the function itself, which crashes ESLint with `expand is not a function`.
- **The Node runtime is one version everywhere**: `.nvmrc` (read by CI through `.github/actions/setup`), both Dockerfiles (`node:24-alpine`) and the three `engines` fields. `@types/node` follows that major, not the newest Node - Dependabot ignores its majors, so bump it together with the runtime.
- **TypeScript and ESLint majors are pinned on purpose** (see the `ignore` block in [.github/dependabot.yml](.github/dependabot.yml)) - re-check these before assuming they are still stuck, the picture moves:
    - **TypeScript 7**: hard-blocked. `typescript-eslint` peers on `typescript >=4.8.4 <6.1.0` as of 8.70.1, and it is the parser behind every type-aware lint rule. TS 6.0.3 is the ceiling until that peer range moves.
    - **ESLint 10**: down to a single blocker. `eslint-plugin-jsx-a11y@6.10.2` caps at `^9` (upstream issue #1075, open since Feb 2026, no fork, no prerelease) and only the frontend uses it. `eslint-plugin-import` also caps at `^9` but the maintained fork `eslint-plugin-import-x` already supports `^10` (rules rename `import/*` → `import-x/*`, ~7 config touch points per side). `typescript-eslint` is no longer a blocker - it allows `^10`. The root config uses neither blocker and could move today. Deliberately not doing a partial migration: splitting the monorepo across two linter majors is worse than waiting. When jsx-a11y ships support, move all three packages plus the `import-x` swap in one maintenance release.
- Commit lockfiles and tool configs. `package-lock.json` (root/backend/frontend) and `eslint.config.js` are tracked - committing them keeps installs reproducible and lets CI run `npm ci`.
- **Never hardcode credentials, API keys, tokens, or passwords anywhere in the repo** - not in code, tests, scripts, docs, commit messages, or PR text. Every secret is read from an environment variable through [backend/src/config/env.ts](backend/src/config/env.ts): locally via the gitignored `backend/.env`, in production via the server's `/srv/cooking-assistant/.env`. A new secret gets a key (no value) in `backend/.env.example`. The only tolerated in-code values are the historical local-dev DB defaults already in `env.ts` and test-only values generated at runtime (see the e2e per-run password) - do not add new exceptions.
- **Never hardcode real domains/emails/infrastructure identifiers** (anything that could collide with real prod data, e.g. `cooking-assistant.app`, server addresses, hosting-provider resource names) anywhere in the codebase, including as "fake" test fixtures - use `example.com`/`localhost`/other generic placeholders instead. Synthetic test literals (passwords, tokens, IDs) are fine inline in test files as-is - they aren't real credentials, so they don't need env-var indirection.
